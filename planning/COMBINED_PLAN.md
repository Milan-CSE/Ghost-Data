## 4. Module contracts and algorithms

**`adapters/*`** — each exposes `parse(path: Path, file_id: str, captured_at: str) -> list[Fact]`.
- `sqlite_dump`: `sqlite3.connect(":memory:")`, `executescript(text)`; enumerate tables; tag each Fact with its `store` (table/replica name); parse `record_json` columns; `covers_system=True` for full tables.
- `json_bundle`: evaluate **each inner snapshot's** `captured_at` (not the container's `exported_at`); skip inner snapshots after `audit_at` (done later by the ledger via `captured_at`).
- `log_*`: one parser per style; map `http_status 404`, `rows=0`, `NOT_FOUND`, `profile: null` to `ABSENT`; logs never set `covers_system` (observation only).
- `png_vision`: calls `llm.extract_image(path)`; Fact list built from the validated JSON; low-confidence rows flagged.
- Every adapter has a unit test using a **real excerpt** copied into `tests/fixtures/`.

**`ledger.py`**
```python
class Ledger:
    def add(self, facts: list[Fact]) -> None
    def admissible(self, audit_at: str) -> "View"          # captured_at <= audit_at (inclusive)
    # View.latest(system_id, resource_id) -> Fact | None
    # View.covering_snapshot(system_id) -> str | None      # file_id of the latest covering store
    # View.by_identifier(identifier) -> list[Fact]
```
Selection rule (per step): latest admissible Fact for that (system, resource); for absence, the latest admissible `covers_system` snapshot for that system. Known sample failure to fix: `case_31` step 1 picked an older SQL dump instead of the newer JSON bundle, so the covering index must span **all formats**.

**`identity.py`** — `build_bag(case, identities, audit_log) -> IdentityBag`
1. Resolve `user_id` by request email (lowercased) against current and historical emails.
2. Reconstruct values at `audit_at` by rolling back audit-log rows with `event_time > audit_at` (restore `old_value`).
3. Search surface = values valid at or before `audit_at` + `sha256(lower(email))` for each email + `user_id`. Never add values that begin after `audit_at`. Exact equality only.

**`ownership.py`** — `link(case, bag, view, activity) -> list[OwnedResource]`
Order of signals: (1) exact identifier match; (2) relational fields (`subject_reference`, `customer_reference`, `source_resource_id`); (3) log traces joined by `trace_id` from a lookup that contains an authoritative identifier; (4) vision rows. Activity (`deletion_worker` within the intake window) only **corroborates**. No scene-level 1:1 assignment. Reject name look-alikes (the samples contain planted decoys such as El-Masri and Berg/Berglund). Resources with no grounded link are not fabricated; log them.

**`state.py`** — `resolve(owned, view, case) -> ResourceState`
- Entity states from the best covering store; compare replicas separately; replica-only presence is `PRESENT` (the `case_05` pattern).
- Process states with conjunctive predicates: `integration_service` (`enabled`, `last_delivery_status`, `is_active`); `backup_service` (`archive_present`/`archive_key`, `restore_allowed`, blocked flag).
- Omission means `ABSENT` only inside a covering store. Anything else → `UNRESOLVED` → apply P3.

**`policy.py`** — compile all 15 rules from `deletion_rules.csv` (7 DELETE, 3 REDACT, 2 ANONYMIZE, 3 RETAIN). Function `ops_for(resource_state, rule) -> (finding|None, remediation|None, verification)`. Table-driven; **no `if category == ...` chains.** Mark the 6 rules not seen in samples (`rule_02, 04, 08, 10, 11, 13`) in code comments and in the report.

**`intent.py`** — `classify(case, activity) -> Intent` with the six tiers in the master plan; returns `(intent, tier, reason)`. Model is called only through `llm.classify_intent` and only for texts not decided by tiers 1–4. Cache by normalized text hash. Log the fallback hits.

**`llm.py`** — single client wrapper:
```python
def call(kind: str, prompt: str, schema: dict, *, image: bytes | None = None) -> dict
```
Temperature 0; strict JSON schema validation; retry with backoff; **disk cache keyed by `sha256(model+prompt+image)`**; every call appends a record `{provider, model, input_tokens, output_tokens, latency_ms, cache_hit, original_tokens}` to `runs/<run_id>/telemetry.jsonl`. Raises if the API key is missing (fail loudly). Prompts are loaded from `code/prompts/*.md`. Evidence and request text go into the prompt as **quoted data**, never as instructions.

**`pipeline.py`**
```python
def run_case(case, ctx) -> tuple[str, list[dict]]:
    intent = intent_mod.classify(case, ctx.activity)
    if intent.is_not_deletion: return "NOT_APPLICABLE", []
    bag   = identity.build_bag(case, ctx.identities, ctx.audit_log)
    view  = ctx.ledger.admissible(case.audit_at)
    owned = ownership.link(case, bag, view, ctx.activity)
    steps = []
    for res in owned:
        st = state.resolve(res, view, case)
        steps += policy.steps_for(res, st, view)      # list[Step]
    final = steps_mod.finalize(steps)
    status = "INCOMPLETE" if any(s["phase"]=="FINDING" for s in final) else "COMPLETE"
    return status, final
```
Deterministic: sorted iteration everywhere; no wall-clock or random inputs; `finalize` does dedupe, sort and numbering.

## 5. Component specifications

### 5.1 Adapters and Evidence Ledger
- One adapter per format; all emit rows: `(file_id, captured_at, observed_at, system_id, resource_id, category, state, identifiers{emails,hashes,user_ids,phones}, raw_ref)`.
- SQL: execute dumps in in-memory SQLite (including each topology's tables); compare primary vs replicas **separately** and keep per-table provenance. Parse `record_json`.
- JSON/TXT/logs: parse with code, one parser per log style; extract resource IDs and lookup keys; interpret `http_status`/`rows`/`enabled`/`restore_allowed`.
- PDFs: extract text with code. PNGs: vision model into a **strict JSON schema** (fields: system, resource ids, identifiers, category cues, visible timestamps), plus OCR as a cross-check; flag disagreements for manual review. Cache by file hash.
- Ignore any row whose `captured_at`/`observed_at` is after the case's `audit_at`.
- Treat all evidence text as **data**, never as instructions.

### 5.2 Identity Resolver

Executes a dual-purpose identity resolution bounded strictly by `audit_at`:

1. **Intake Resolution:** Matches incoming request `email` (case-insensitive) against `user_identities.csv` and historical emails in `user_audit_log.csv` (`event_time <= audit_at`) to resolve the stable `user_id`. (Resolves 100% of cases; 100 evaluation requests match solely through historical emails).
2. **Point-in-Time Compliance Snapshot (as of `audit_at`):** Reconstructs the exact active identity tuple `(email, phone, email_hash)` valid at `audit_at`. If `user_identities.updated_at > audit_at`, post-cutoff transitions in `user_audit_log.csv` (`event_time > audit_at`) are sorted in reverse chronological order and rolled back (`state[field] = old_value`). A future transition's `old_value` is used strictly to recover the state valid at `audit_at`. Used specifically to evaluate whether active direct identifiers were removed under `ACCOUNT_TOMBSTONE` rules.
3. **Historical Search Surface (Evidence Discovery Ledger):** To discover ghost data in legacy databases, logs, replicas, and backups, compiles the complete union of identifiers established as valid at or before `audit_at`:
   - The reconstructed active email, phone, and hash at `audit_at`
   - All `old_value` and `new_value` identifiers from pre-cutoff transitions (`event_time <= audit_at`)
   - The stable `user_id` and known `subject_reference` aliases
   - `sha256(lowercase(email))` for every valid historical email
4. **Post-Cutoff Leakage Exclusion & Temporal Boundary:** Identifiers whose only validity begins after `audit_at`—specifically the `new_value` of any transition where `event_time > audit_at`—are strictly excluded from the historical search surface. A future transition's `old_value` is not automatically added to the search surface unless independently established as valid at or before `audit_at`. This prevents post-cutoff identifiers from leaking into historical evidence searches.

*Canonical Sample Metric Clarification:* The dual-purpose model achieved 32/32 on **Identity Resolution & Cited Evidence Reachability on Canonical Samples** (matching all 32 users and ensuring historical identifiers such as `case_10`'s `nadia.ionescu@yahoo.com` reach cited ghost data in `evidence_61`). This metric confirms identity and evidence reachability only; it does not claim full end-to-end sample-output accuracy, as the complete 193-step output was not reconstructed or compared end-to-end.

### 5.3 Ownership Linker (H1)

Produces, per case, the set of owned resources per system grounded strictly in authoritative, participant-visible signals:

1. **Deterministic Primary Signals (Exact Identifier & Relational Grounding):**
   - Exact match between evidence attributes and the user's dual-purpose identity ledger (`user_id`, reconstructed active email/phone/hash at `audit_at`, and pre-cutoff historical emails/phones/hashes).
   - Relational attributes and foreign keys in structured evidence (`subject_reference`, `customer_reference`, `source_resource_id`).
   - Log trace correlation: uniquely correlating structured log events where a lookup request containing an authoritative user identifier (e.g., `lookup_key`, `match_key`, `subject_ref`) shares an explicit, unique `trace_id` with a resulting resource event.
2. **Corroborating Workflow Activity Signals:**
   - Resources processed by `deletion_worker` in `dataset/system_activity.csv` during the case's verified intake window `[requested_at, reported_at]`.
   - Timing alone must never establish ownership; activity logs serve strictly to corroborate resources identified via system schema or lookup traces.
3. **Decoy Rejection & Anti-Assignment Rule:**
   - Strict rejection of fuzzy/partial name or email matches (e.g., `Karim El-Masri` vs. `Amina El-Masri` in `evidence_54`; `Joana Berg` / `Jonas Berglund` vs. `Jonas Berg` in `evidence_57`).
   - The scene-level one-to-one constraint must **NEVER** be used as an assignment heuristic to force-link unowned or decoy records to a user whose data has already been deleted.
4. **Cardinality Scope & Shared Resources:**
   - Do not impose a universal one-resource-per-user-per-system constraint. Enforce ownership exclusivity only where the resource schema and policy establish that the resource is single-owner (e.g., primary account profile).
   - Shared resources (e.g., multi-party support tickets, shared contact contexts) may legitimately concern multiple users. Where permitted by policy, legitimate secondary resources must not be artificially truncated.
5. **Handling of Unresolved Targets:**
   - Where ownership is unresolved, the linker must never fabricate an unevidenced link.
   - *Empirical Target Grounding on 32 Canonical Samples (111 Targets Reconciled):*
     - 92 targets (82.88%) are explicitly established via direct or structured evidence links.
     - 16 targets (14.41%) are supported by independently validated combinations of intake activity and service schema lookups.
     - 2 targets (1.80%) require multimodal image interpretation (admin console PNG screenshot `evidence_04`).
     - 1 target (0.90%, `case_04` / `account_004`) is not grounded by currently identified evidence or activity (the account was deleted prior to the sample activity window and is absent from `evidence_54`). This target remains an explicit unresolved limitation; the engine must not use canonical ground truth or case-specific naming shortcuts in production logic.

### 5.4 State Reconstruction

For each owned resource, the state at `audit_at` is established by identifying the latest admissible observation captured at or before `audit_at` (`captured_at <= audit_at`) from the best-covering source for that system. Reported activity results, workflow statuses, and system messages are claims: they provide operational context and candidates for investigation, but never constitute proof of state without grounded evidence.

1. **Snapshot Selection & Temporal Boundaries:**
   - **Dual Timestamp Evaluation:** In multi-snapshot bundle files (e.g., JSON bundles under `evidence/records/`), eligibility is governed strictly by the internal snapshot's own `captured_at` timestamp, not the container's `exported_at` date.
   - **Exact-Timestamp Admissibility:** Observations where `captured_at == audit_at` are admissible (verified across 15 canonical sample steps). Any observation with `captured_at > audit_at` is strictly inadmissible.
   - **Cross-Format Covering Index (Design Rule):** The prototype single-format snapshot selector achieved 74/75 (98.7%) on canonical samples, failing in `case_31` Step 1 (`account_service` / `account_4857`) where it selected `evidence_54` (an older SQL dump at `2026-09-02T23:00:00Z`) over `evidence_51` (a newer JSON snapshot bundle at `2026-09-15T12:00:00Z`). This failure is an unresolved limitation of the prototype. The solver engine must implement cross-format covering indexing across SQL, JSON, text records, and log streams. *(Note: Cross-format indexing is a required design rule; this experiment did not verify that the fix works).*

2. **Replica Topologies & Cutoff State Uncertainty:**
   - **Topology Roles:** The engine must distinguish operational replicas (`failover_replica`, `read_replica`, `regional_replicas`, `reporting_replica`), which serve platform traffic, from catalog/inventory snapshots (`customer_data_inventory`).
   - **Last Observed State vs. Cutoff State:** Observing a surviving record in an operational replica at $T_1 \le \text{audit\_at}$ establishes the last observed state at $T_1$. If subsequent state through `audit_at` cannot be established from evidence or proven activity, the cutoff state must be treated as `UNRESOLVED` rather than asserting `PRESENT`.
   - **Intervening Activity Scope:** An intervening deletion event between $T_1$ and `audit_at` can only transition the state to `ABSENT` if the event explicitly proves successful deletion for that specific resource across that specific replica's scope (e.g., primary-only deletions do not clear failover replica drift).

3. **Absence vs. Non-Coverage:**
   - A resource is verified `ABSENT` only when omitted from an authoritative, covering data store (a complete database table or full snapshot bundle for that system).
   - Point queries, incremental logs, and diagnostic traces establish only observation or non-observation; they cannot prove global absence unless they record an explicit 404 or missing-record response for that resource.

4. **Process Predicates (Design Rules):**
   - Entity states (`PRESENT`, `ABSENT`, `REDACTED`, `ANONYMIZED`) and process states (`ACTIVE`, `DISABLED`, `BLOCKED`) must remain strictly segregated.
   - **`integration_service`**:
     - `ACTIVE` (`REPORT_ACTIVE_DATA_FLOW`): `enabled == true` AND `last_delivery_status != 'stopped'` AND `is_active == 1`.
     - `DISABLED` (`VERIFY_DATA_FLOW_DISABLED`): `enabled == false` AND (`last_delivery_status == 'stopped'` OR `is_active == 0`).
     - Contradictory or missing signals: Must evaluate to `UNRESOLVED`; silent transitions to `ACTIVE` or `DISABLED` are strictly prohibited.
   - **`backup_service`**:
     - Archive existence requires `archive_present == true` OR a populated `archive_key`. Archive absence must never be inferred merely because archive evidence was not found (unobserved != absent).
     - `ACTIVE` (`REPORT_RESTORE_RISK`): Archive exists AND `restore_allowed == true` AND explicit confirmation that restore is unblocked (`is_blocked == 0` or explicitly unblocked). Missing or conflicting blocking status fields cannot establish that an archive is unblocked.
     - `BLOCKED` (`VERIFY_RESTORE_BLOCKED`): Archive exists AND (`restore_allowed == false` OR `is_blocked == 1`).
     - Missing archive existence signals or contradictory blocking flags: Must evaluate to `UNRESOLVED`.

5. **Grounded Evidence & Limitations:**
   - Every finding and complete-case verification step must cite the participant-visible `file_id`, `activity_id`, or `audit_id` that proves it.
   - Resources that cannot be grounded from available evidence (e.g., `account_004` in `case_04`) must not have fabricated citations or states; unevidenced resources remain documented architectural limitations.
   - Administrative console screenshots (`evidence_04`) require multimodal vision processing to reconstruct state.

### 5.5 Policy Compiler (Category + Observed State → Operations)

The Policy Compiler deterministically maps each owned resource's observed state at `audit_at` to the required finding, remediation, and verification operations defined in `AGENTS.md` §6.4, driven by the 15 policy rules in `deletion_rules.csv`.

1. **Structural Cardinality & Policy Conditions:**
   - **Total Rules:** Exactly 15 policy rules across 15 distinct data categories and 9 distinct conditions.
   - **Action Distribution:** Exactly 7 `DELETE` rules (`rule_01`, `02`, `03`, `04`, `06`, `09`, `10`), 3 `REDACT` rules (`rule_05`, `11`, `15`), 2 `ANONYMIZE` rules (`rule_07`, `08`), and 3 `RETAIN` rules (`rule_12`, `13`, `14`).
   - **Seen vs. Unseen Classification:**
     - Exactly 9 rules are **empirically verified on canonical samples** (`rule_01`, `03`, `05`, `06`, `07`, `09`, `12`, `14`, `15`), plus operational process flows (`DATA_FLOW`).
     - Exactly 6 rules are **unseen in canonical samples** (`rule_02`, `04`, `08`, `10`, `11`, `13`). Their transitions are designated as **DERIVED DESIGN RULES — UNVERIFIED ON SAMPLES**.
     - `rule_10` (`MARKETING_PROFILE`) remains classified as unseen; `case_12` (where `analytics_9914` was deleted via `DELETE_RECORD`) is recorded as ambiguous category attribution (e.g., an un-anonymizable contact lookup entry in analytics), not verified `MARKETING_PROFILE` rule coverage.

2. **Retained Record Invariants & Separation (`SECURITY_AUDIT_LOG` vs. `LEGAL_HOLD_RECORD`):**
   - Retained records required by policy never produce findings or deletion/redaction remediations; they emit exclusively `VERIFY_RECORD_PRESENT` (`state == "PRESENT"`).
   - **`SECURITY_AUDIT_LOG` (`rule_12`):** Empirically verified across 24 canonical sample cases (7 COMPLETE, 17 INCOMPLETE). In 100% of occurrences, it emitted `VERIFY_RECORD_PRESENT` with `state == "PRESENT"` (zero findings, zero remediations).
   - **`LEGAL_HOLD_RECORD` (`rule_13`):** Strictly separated from empirical audit log findings. Formulated as a **DERIVED DESIGN RULE — UNVERIFIED ON SAMPLES** that enforces the identical invariant (`VERIFY_RECORD_PRESENT`, state `PRESENT`, zero findings/remediations).

3. **Tombstone Dual-State Rigor (`ACCOUNT_TOMBSTONE`, `rule_15`):**

### 5.6 Ordering, Evidence IDs, and Output Serialization

1. **Macro Phase Order:**
   - All steps strictly follow the sequential order: `FINDING` → `REMEDIATION` → `VERIFICATION`.
   - `COMPLETE` cases contain exclusively `VERIFICATION` steps (34 steps across 10 sample cases). `INCOMPLETE` cases contain all three phases consecutively (41 findings, 41 remediations, 77 verifications across 22 sample cases). Measured phase order violations on canonical samples: 0 / 193 steps (100.0% adherence).

2. **Intra-Phase Step Sequencing & Tie-Breaking (Inferred Deterministic Rule):**
   - Steps within each phase are deterministically sorted by: `phase_rank` → `operation_rank` → `system_id` ascending → `resource_id` ascending.
   - **Status of Hierarchy:** This hierarchy is an **inferred deterministic design rule** derived from the 32 canonical samples (achieving 193/193 steps and 32/32 cases exact agreement), rather than a sequence explicitly mandated in its entirety by the competition rules.
   - **Operation Sequence within Phases:**
     - **`FINDING`:** `REPORT_REMAINING_RECORD` (Rank 10) → `REPORT_EXPOSED_PII` (Rank 20) → `REPORT_ACTIVE_DATA_FLOW` (Rank 30) → `REPORT_RESTORE_RISK` (Rank 40).
     - **`REMEDIATION`:** `DISABLE_DATA_FLOW` (Rank 110) → `BLOCK_RESTORE` (Rank 120) → `DELETE_RECORD` (Rank 130) → `REDACT_RECORD` (Rank 140) → `ANONYMIZE_RECORD` (Rank 150).
     - **`VERIFICATION`:** `VERIFY_RECORD_ABSENT` (Rank 210) → `VERIFY_RECORD_PRESENT` (Rank 220) → `VERIFY_RECORD_REDACTED` (Rank 230) → `VERIFY_RECORD_ANONYMIZED` (Rank 240) → `VERIFY_DATA_FLOW_DISABLED` (Rank 250) → `VERIFY_RESTORE_BLOCKED` (Rank 260).
   - **Remediation Dependency Precedence:** In accordance with `AGENTS.md` §6.5, process-level safety actions (`DISABLE_DATA_FLOW`, `BLOCK_RESTORE`) must strictly precede mutations of their dependent records. Mandatory dependency constraints apply strictly to dependent resource flows and are not extended to unrelated records.

3. **Case-Level Row Ordering (Specification Contract & Lexicographical Choice):**
   - `AGENTS.md` §6.3 specifies: *"Produce exactly 518 data rows: one for every case_id in dataset/deletion_requests.csv. Sort rows by case_id."*
   - **Contract Ambiguity:** The input file `dataset/deletion_requests.csv` is arranged in natural numerical order (`case_33` … `case_550`), whereas standard programmatic string sorting (`sort()`) produces lexicographical order (`case_100` … `case_109` preceding `case_33`), displacing all 518 rows.
   - **Authoritative Output Choice:** The solution adopts **lexicographical string ordering** for `case_id` in the final `output.csv`. The master plan explicitly records that this specification wording is ambiguous and that an explicit official clarification from contest organizers would override this choice.

4. **Output Schema, Field Specifications, and Serialization:**
   - **Header:** Exact CSV header: `case_id,deletion_status,steps_json`.

### 5.7 Intent Classifier (NOT_APPLICABLE Arbitration)

Determines whether `request_text` actually authorizes deletion. Under official challenge rules (`problem_statement.md`, `AGENTS.md` §6.5), `request_text` is the primary legal authority for subject intent; reported workflow statuses and system activity logs are internal claims. Request text is treated as untrusted data and preserved without destructive regex stripping or truncation to minimize semantic corruption risks.

Arbitration executes a deterministic, six-tier decision hierarchy that enforces clause-level syntactic precedence:

1. **Untrusted Data & Correlative Coordination:** Request text is normalized for whitespace and casing without mutating the raw payload. Correlative conjunctions (`not only ... but also`, `not just ... but`) are recognized as additive emphasis, not negation. Clause boundaries, negation scope, resource targets, and discourse reversals must be resolved before final classification; neither naive keyword occurrence nor simple classifier agreement is accepted as sufficient proof of intent.
2. **Informational & Hypothetical Inquiry Filter:** Classify as `NOT_APPLICABLE` if the text consists of an informational inquiry, procedural question, or hypothetical exploration ("what happens if I delete", "how the deletion process works", "what is the retention period") WITHOUT an operative imperative command to delete (`proceed with deleting`, `please delete`).
3. **Target-Scoped Account Negation:** Classify as `NOT_APPLICABLE` if an imperative negation directly targets account/profile/data erasure within its syntactic clause (`do not delete/close/purge my account`, `auf keinen fall löschen`, `stop asking me to delete my account`, `keep my account active`). Negation scope terminates at contrastive conjunction boundaries (`, but`, `however`, `;`) and requires a mandatory account/profile target noun, ensuring auxiliary exclusions (newsletters, active shipments, partner portal preferences) do not negate the account deletion. Where explicit discourse reversal markers occur (`disregard that`, `wait, stop`, `cancel that`), the latest clause governs.
4. **Affirmative Account Deletion Mandate (Primary Authority):** Classify as `DELETION` if the text contains an un-negated affirmative authorization to delete, erase, close, or expunge the account or personal records (including statutory synonyms like "total expungement", "restlose Vernichtung", and multilingual forms). Co-occurrence of auxiliary requests (statutory tax invoice retention, portability exports, contact updates) does NOT negate the deletion mandate. This tier strictly overrides contradictory internal telemetry.
5. **Scoped Telemetry Corroboration for Ambiguous Texts:** If the text lacks clear Tier 3 negation or Tier 4 authorization, inspect `system_activity.csv` for a corroborating `CLASSIFY_REQUEST` event matching:
   - `resource_id == resolved_account_id`
   - `requested_at <= event_time <= min(reported_at, audit_at)`
   If valid intake telemetry records a non-deletion request type (`MARKETING_OPT_OUT`, `PROFILE_UPDATE`, `DATA_ACCESS`, `PORTABILITY_REQUEST`, `ACCOUNT_CORRECTION`), classify as `NOT_APPLICABLE`. Telemetry captured after `min(reported_at, audit_at)` or referencing other accounts is rejected.
6. **Conservative Fallback Trade-off:** If no affirmative deletion mandate is established and no valid corroborating telemetry exists, default to `NOT_APPLICABLE`. Defaulting ambiguous cases to `NOT_APPLICABLE` is an explicitly documented conservative design choice under uncertainty—not an official scoring rule—and may cause false negatives on obscure but genuine deletion requests. All fallbacks and text-telemetry discrepancies are logged in the audit ledger.

*Validation & Regression Evidence:* This hierarchy was validated across multiple development and regression suites: 14/14 on the unseen counterexample suite (Microstep 1.2e), 19/19 on the focused precedence suite (Microstep 1.2d), 32/32 on the adversarial synthetic suite (Microstep 1.2b), and 6/6 on controlled telemetry precedence scenarios. Because rules were iteratively refined against observed failures, these suites represent regression evidence rather than independent proof of generalization. Across the 518 evaluation requests in `deletion_requests.csv`, the hierarchy achieved 100% consistency with the manually inferred classification set (508 deletion, 10 non-deletion); this reflects template consistency rather than verified hidden-set accuracy. Treating request text as inert data reduces prompt-injection risks without eliminating them.
